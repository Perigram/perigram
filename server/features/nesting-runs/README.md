# COMPONENT: Nesting Runs

Stores the digital solutions generated by the nesting algorithms.

## v24 Architecture
- **Digital Bridge**: Connects a `Queue` intent to a specific material layout.
- **Lineage**: Cumulative trace inheriting from Project and Queue (`lineage.runId` used for child artifacts).
- **Status**: Governed by `NestingRunMachine` (NESTING -> COMPLETE | ERROR | CHOSEN).
- **UI Components**:
  - `NestingRunCard`: Supports `card`, `inline`, and `compact` variants and
    renders run metrics, accepted material sources, and related sheet designs.
  - Smart Actions: lifecycle/status actions come from the status API and
    generated process action manifests; destructive controls require
    entity-scoped `nesting_runs` admin/delete access for the concrete run.

## Key Workflows
1. **Proposal**: Created automatically by the `Nesting Processor` at workflow
   initial status, then completed through the `nestingSolveCompleted` intent
   when a legacy queue helper already has solver results.
2. **Review**: Exposes standardized artifacts (DXF, PDF) for efficiency and layout evaluation.
3. **Acceptance**: `COMPLETE -> CHOSEN` is a normal status transition. The
   transition runs a synchronous feature preflight before the status snapshot is
   written, then emits effects that apply production output through the queue
   service after the run becomes `CHOSEN`. The queue-specific choose endpoint is
   a compatibility facade over this transition. Production acceptance is
   represented by the chosen run plus `queue.data.materialConsumption` /
   `queue.data.physicalOutputs`; choosing/rejecting runs is authorized through
   the concrete `nesting_run` status/action grant. Queue effects execute after
   that run-level authorization and must not make parent `queues:write` imply
   visibility or control over every run.
4. **Physical Bridge**: Transition from `VIRTUAL` mode to `WAREHOUSE` via material matching action.

## Data Structure
```typescript
{
  runNumber: Number,
  materialMode: Enum(VIRTUAL, WAREHOUSE),
  params: { width, height, space, sheetCount, inventoryItems?, sheet_polygon? },
  origin: StatusBlock,
  status: StatusBlock,
  lineage: { organizationId, projectId, queueId },
  data: {
    results: { sheetCount, placedCount, efficiency, remnantArea },
    layoutData: Object,
    sheetDesignIds: Array<String>,
    error?: String
  },
  requestedArtifacts: Array<String>
}
```

## Runtime Notes
- DXF generation requires `MONGO_DB_NAME` if the Mongo URI lacks a default DB.
- Runs must include `lineage.queueId` for UI/API filtering.
- List and detail APIs filter by entity-scoped `nesting_runs:read` grants on
  the loaded run DTO, not only by parent queue lineage. This preserves
  status-scoped process windows such as "read completed runs" without leaking
  unknown or unrelated run states through queue details.
- List filters accept queue/project lineage ids plus queue-style
  `primaryStatus` and comma-separated `primaryStatuses`, both translated to the
  canonical `status.state.primary` block field before repository queries. Chat
  attachment pickers and generated process screens rely on this contract for
  status-gated run lists.
- Completed nesting runs link to generated sheet layouts through
  `data.sheetDesignIds`. Each ID points to a separate `sheet_design` for one
  physical worker layout; the run keeps the full enriched worker result under
  `data.layoutData` for traceability.
- Process-authored `nesting_run` statuses are merged with domain system
  transitions at runtime. The solver lifecycle still uses hidden
  `NESTING -> COMPLETE` and `NESTING -> ERROR` intents so runs created by
  queue nesting never remain in an unknown process state after the worker
  returns successfully.
- Process `solveNesting` execution returns `nesting_run` entity refs. The
  process action runtime reads the active graph edge from the command output to
  the downstream status node and writes that process-authored state to the run
  before generated screens reload. Existing runs can be repaired with
  `server/scripts/migrate-process-command-output-statuses.js`; the migration is
  graph-derived and does not hardcode statuses such as `COMPLETE` or
  organization-specific labels.

# COMPONENT: Artifacts

Persisted metadata entity for generated files and uploaded previews. The
framework contract term for file behavior is `AttachmentKind`; `artifact` is the
current app entity type that stores file metadata and GridFS references.

Parent: [server/features](../README.md).

## Responsibilities

- Create generation requests through `generateAttachment`.
- Store primary file metadata under `attachments.primary`.
- Stream files from kind-specific GridFS buckets.
- Return artifact DTOs for Workbench and preview UI.
- Render optional organization artifact templates and pin the exact template
  revision in artifact provenance.
- Create immutable artifact layout revisions when a template-backed artifact is
  generated or its placed items are moved/deleted.
- Create immutable `file` revisions for every uploaded, captured, rendered,
  edited, replaced, or restored artifact file. Each file revision retains its
  own GridFS attachment; artifacts point at the current revision through
  `data.revisions.file`.

Creation and editor selection are domain concerns, not persistence concerns.
The domain `AttachmentKind` contract states whether a kind is uploaded,
generated by a command, or produced by workflow, and whether it supports the
layout editor. This feature persists and serves the resulting artifact without
inventing a generic entity-create path or choosing a frontend editor.

## APIs

- `POST /api/artifacts` — multipart upload for a declared upload-backed kind
- `PUT /api/artifacts/:id` — update writable artifact identity/data
- `PUT /api/artifacts/:id/file` — replace the file of an upload-backed kind
- `GET /api/artifacts/:id`
- `GET /api/artifacts/:id/metadata`
- `DELETE /api/artifacts/:id`
- `POST /api/artifacts/:id/revisions/:revisionId/restore`
- `GET /api/instance-revisions/:id/file`

Upload requests carry the declared kind, file, name, and parent lineage. The
service owns file metadata such as the original filename; clients do not edit
that storage object as arbitrary JSON. When a process owns the artifact
lifecycle, the hidden `artifactFileStored` system intent is recorded without
replacing the process-authored current state.

Before authorizing an artifact create, the service resolves the organization's
initial Artifact status and evaluates the `create` permission against that
status and the requested Lineage. This lets status-scoped process grants
authorize their declared constructor output without bypassing the shared access
engine or checking an incomplete pre-status DTO.

Upload and replacement routes enforce each attachment kind's allowed extension,
MIME type, and byte limit. Deleting an artifact as an administrator cascades to
its revisions and retained GridFS blobs.

## Generation Notes

`generateAttachment()` resolves everything from declarations:

- The `kind` options are the attachment kinds whose vocabulary entry
  declares command creation (`commandCreatedKinds`,
  [attachment kinds](../../../shared/attachment-kinds.js)) — never a
  frozen list in the command definition.
- With `entities.template` (an `artifact_template`), generation delegates
  rendering to the template feature and requires the requested kind to
  match the format (`LAYOUT_DXF` for DXF, `PDF_PASSPORT` for PDF). Values
  are validated against the selected revision's typed variables. The
  artifact stores the rendered file immediately, keeps editable
  layout/values under `data`, and pins the source and template revision
  under `provenance`. PDF generation requires `entities.template`.
- Otherwise the org's installed plugin export bindings are the whole
  truth: the source instance's actual type must match a `(typeId, kind)`
  binding exactly — no spelling rewrites, no any-type fallback — and the
  bound plugin service returns the file, stored in the kind's declared
  bucket with the kind's declared MIME. The source-lineage key derives
  from the type id (camelCased) — one law for every type.

`PUT /api/artifacts/:id/layout` creates a new artifact layout revision and
replaces the rendered file.

## Conversion

`convertArtifact` is an artifact command backed by the
[artifact-conversions](../artifact-conversions/README.md) capability, which
owns the conversion catalog and the `POST /api/artifact-conversions` route.

* DONE Process designer architecture and UX acceptance
  [2026-08-02 Sun]

  This is the current plan for the organization process designer. Presence in
  the runtime catalog or a source-code assertion does not make a node usable.
  A capability is accepted only when a user can build, understand, validate,
  save, and run its complete process in the UI.

  Use domain and project vocabulary in the UI. In particular, do not introduce
  entity categories such as "normal" and "derived". Some entity types have
  more than one domain-declared way to create them; that is a Create Entity
  configuration concern, not a new kind of entity. "Select Entities" means
  obtaining existing readable entities as data. "Run Service" means running a
  registered command and must show that command's actual inputs.

** Required system boundaries

   The node set must remain separated by what data it handles:

   - value nodes create or transform primitive values;
   - list/tree nodes reshape or align collections without knowing about
     entities;
   - entity and block nodes read, compose, or persist canonical entity data;
   - execution connections decide when state-changing nodes run.

   The primary palette has four understandable families: Entities, Values,
   Lists and trees, and Automation. Logic, Text, Math, and Date belong to
   Values. Status definitions and persistence belong to Entities. Automation
   is intentionally limited to usable entity/domain event entries and Wait
   Until; it is not an exhaustive control/runtime palette.

   Item, list, and tree are transport shapes, independent from the underlying
   value type. Safe widening may happen on a connection. Narrowing, parsing,
   nullable removal, and structural changes must be explicit and must never
   create unexplained Cast, Convert, Trigger Payload, predicate, patch, or
   other internal nodes in the authoring palette.

   Each public node must have a documented purpose, input contract, output
   contract, inline fallback behavior, inspector configuration, validation
   behavior, and runtime behavior. Empty nodes and settings without an effect
   are defects.

** DONE Publish and enforce the authoring capability matrix

   Audit the curated palette against the compiler and evaluator. For every
   supported user operation, record the exact authoring path and identify any
   runtime-only operations that must remain hidden.

   The matrix must cover at least:

   - creating every domain entity type through Create Entity;
   - selecting existing entities and filtering them using their data;
   - reading, composing, and modifying every supported canonical block;
   - changing entity status;
   - running every registered service with its declared inputs;
   - starting an effect manually or from an execution connection;
   - calculating a future date and continuing execution on that date;
   - applying item, list, and tree operations with defined alignment rules.

   Remove authoring entries that cannot participate in one of the documented
   paths. Add only operations required to complete a path; do not expose the
   exhaustive runtime catalog as a second or advanced palette.

   Acceptance evidence is layered: compiler/evaluator/orchestration tests own
   semantic behavior, catalog tests own generated sockets, and browser tests
   own interaction paths that require a real canvas. One browser test per
   matrix row is redundant and is not the primary semantic proof.

** DONE Complete Select Entities and field-based filtering

   Provide one clear source for existing entities. Select Entities chooses an
   entity type, respects process access and organization scope, and outputs a
   typed entity list. It must not hide a second predicate language inside the
   node.

   Filtering remains ordinary dataflow:

   1. Select Entities produces the original entity list.
   2. Deconstruct Entity, Get Block, or Get Field reads the compared value over
      that list.
   3. Logic produces an aligned Boolean mask.
   4. Filter List receives the original list and mask.

   Define empty-list behavior, item broadcasting, list alignment, tree paths,
   missing fields, nullable values, and access failures. Reject incompatible
   masks without changing the saved graph.

   Acceptance: author and run examples that select entities by status, compare
   a text/number/date field, combine multiple Boolean conditions, and filter by
   a relation or lineage reference.

** DONE Make Create Entity cover every declared creation path

   Create Entity first selects the entity type. The selected domain entity then
   determines its supported creation choices and their real inputs. If an
   entity has several creation choices, choose among them inside Create Entity;
   do not add one-off palette nodes such as Upload DXF, From library cassette,
   or Create cassette template, and do not invent a second entity category.

   Reconcile every domain-declared creation choice with canonical block
   composition. The node must expose only inputs that the selected creation
   choice actually consumes. It must not expose arbitrary leaf fields such as
   name or parent, unexplained null selectors, or guessed attachment inputs.
   Constructed blocks connect as blocks. Specialized service inputs appear only
   when that domain creation choice genuinely requires them.

   Manual access is configured as explicit process-role and access-level rows
   in the inspector. Role assignment must not disappear, be flattened into a
   generic selector, or be moved into an unrelated panel.

   Acceptance: each registered entity type and each of its creation choices can
   be configured, validated, and executed from a fresh graph. Generated manual
   forms and automatic execution use the same declared input contract.

** DONE Finish entity and block composition semantics

   Keep the responsibilities explicit:

   - Deconstruct Entity accepts an entity and outputs its declared blocks.
   - Get Block accepts an entity and outputs one selected block.
   - Get Field accepts a block and outputs one selected field value.
   - Compose Block creates one block from connected values or inline fallbacks.
   - Modify Block accepts a block and replaces only connected fields.
   - Create Entity accepts constructible blocks and status.
   - Modify Entity accepts an entity, writable replacement blocks, and status.

   Compose Block, Modify Block, and Get Field select a canonical block, not an
   entity. A block value does not acquire an artificial owning entity type.
   Fixed blocks obtain fields from their canonical block schema. Open blocks
   author stable entries according to the block's own contract: for example a
   Lineage entry has a key and referenced entity type, while a Relations entry
   additionally declares one/many cardinality. Do not aggregate fields from all
   entities and do not derive a block node's fields from a connected consumer.

   Design a schema-backed discovery UI so users do not have to memorize field
   keys. It may show where a canonical entry is accepted, but it must preserve
   the block's independent meaning and must not mutate sockets according to an
   incidental downstream connection.

   At Create/Modify Entity, validate every connected block entry against the
   selected entity schema:

   - path membership and constructible/writable access;
   - referenced entity type for Lineage and Relations;
   - one/many cardinality for Relations;
   - narrower enum, attachment, array-item, unit, or other declared qualifiers.

   Acceptance: validation rejects a =warehouse= reference connected to
   =lineage.projectId= while creating a queue, before activation. Matching
   entity-independent blocks continue to compile and evaluate.

** DONE Restore status definition authoring

   Create Status remains an Entities-palette operation and creates a visible
   status definition on the canvas. The node edits the status identity and
   exposes one status output socket that can connect to Create Entity or Modify
   Entity. Renaming the visible status must preserve its stable reference and
   existing wires.

   Do not move status creation into the inspector, process selector, Roles, or
   another unrelated plane. The inspector may hold secondary presentation and
   lifecycle evidence settings, but it must not hide the definition itself or
   remove its output.

   Acceptance: create, rename, connect, save, reload, and use a status in both
   Create Entity and Modify Entity. The status output and wires survive reload.

** DONE Finish Value, Logic, Text, Math, and Date nodes

   Value Input is one node with a type selector and the correct compact editor
   for that type. Logic, Text, Math, and Date are one node each with an operation
   selector. Each selector lists only operations valid for the connected or
   selected types and gives the sockets meaningful names.

   Every unconnected input that can sensibly accept a literal has a compact
   inline fallback. A connection overrides that fallback. Required unresolved
   inputs are reported during validation, not as warnings on every new node.
   Complex secondary configuration belongs in the inspector.

   Date operations must support useful entity-based automation, including:

   - reading a lifecycle/status entry timestamp from an entity;
   - adding or subtracting a duration such as 30 days;
   - comparing dates and date-times with explicit timezone behavior;
   - feeding the calculated result to the execution wait described below.

   Acceptance: build and run a graph that reads an entity's status-entry date,
   adds 30 days, and continues an effect on the resulting date.

** DONE Make Run Service expose the selected service contract

   Run Service selects one registered command/service. Its sockets must be
   projected from that command's current declared input contract, including
   required/optional state, value type, entity type, and item/list shape. Do not
   replace these inputs with one unexplained =parameters= record socket.

   Primitive inputs receive inline fallbacks where appropriate; entity, block,
   list, attachment, and other structured inputs remain typed connections or
   use the corresponding shared picker when manual input is supported.

   Acceptance: every registered service can either be configured from a fresh
   graph or is explicitly excluded from process authoring with a documented
   reason. At least one service with multiple typed inputs must be exercised
   through both manual and automatic execution.

** DONE Restore a coherent execution and event model

   Every state-changing node has one compact execution section at the bottom:

   - Manual makes the operation available to authorized users.
   - Automatic exposes one incoming execution socket.

   The switch chooses only between those two modes. It must not list webhook,
   schedule, entity-change, domain-event, or other trigger implementations as
   if they were equivalent effect modes. A successful effect exposes one
   clearly placed completion output. Retry exhaustion fails the run; it is not
   an arbitrary =if failed= graph branch.

   Separately define how a process receives an external event and turns it into
   an execution connection. Include only domain-declared, usable event sources
   and label their payload data explicitly. These usable starts and Wait Until
   live in the curated Automation group; internal trigger-payload plumbing
   remains hidden.

   Provide an explicit Wait Until operation that accepts a date/date-time and
   continues execution when it is reached. Its placement and connections must
   follow the same left-to-right socket rules as the rest of the graph.

   Acceptance: demonstrate manual execution, one effect following another, one
   domain/entity event starting a process, and the calculated 30-day wait flow.

** DONE Complete draft, validation, and activation UX

   Provide persistent New Draft, Save Draft, Validate, and Activate actions.
   They must remain reachable while editing Nodes, Roles, Screens, or an empty
   canvas, rather than appearing only when an arbitrary node is selected.

   Show dirty, saving, saved, validating, validation-failed, and activating
   states. Activation requires successful validation, and the UI must make the
   boundary between saving a draft and applying it to the organization clear.

   Acceptance: edit each designer plane, save without activation, validate,
   locate and fix errors, and activate without selecting a node.

** DONE Make the workspace compact, consistent, and responsive

   Reduce node chrome and use consistent socket rows. Socket dots belong on
   stable outer rails beside their labels; do not print full data-type strings
   beside every socket. Type, shape, qualifiers, and help remain available by
   hover/focus and assistive text. Node headers, icons, colors, spacing, and
   execution sections must communicate concern consistently.

   Make palette and inspector independently collapsible. Preserve a useful
   canvas and reachable primary actions on narrow laptops and supported tablet
   widths. Derive empty-state and toolbar placement from visible rails instead
   of fixed offsets.

   Preserve Blender-like canvas behavior already required by the design:

   - two-finger touchpad pan and pointer-centered pinch zoom;
   - Space plus left drag as an alternative pan control;
   - zoom from 0.1x to 4x, frame-all, and frame-selection;
   - box selection, additive selection, and Delete/Backspace for every selected
     node and edge;
   - right-click canvas palette and compatible-node creation after dropping a
     socket on empty canvas.

   Entity selectors follow the shared picker contract: selected entity cards
   render outside the input, while the compact chevron remains a separate
   trigger. Scalar schema, operation, role, and enum selectors remain ordinary
   controls and must not masquerade as entity pickers.

   Acceptance: run the complete scenario suite at supported wide and narrow
   layouts, using mouse, touchpad, and keyboard paths where applicable.

   These findings describe the pre-implementation baseline retained for audit:

   - The focused designer/validation spot check passed 16 tests, but the UI
     suite primarily checks source strings and is not acceptance evidence.
   - =npm run framework:manifest= reports that the committed manifest differs
     from current generated metadata while source validation succeeds.
   - Consumer validation currently checks open-block paths and access but not
     all declared type qualifiers.
   - The authoring palette currently lacks complete fresh-graph paths for
     selecting entities, some domain-declared creation choices, automatic
     event/date execution, and services requiring structured inputs.

   - The component README publishes the implemented capability matrix and the
     four-family curated palette boundary.
   - Catalog tests cover typed construction and registered command sockets;
     validation tests reject incorrect open-block qualifiers; orchestration
     tests cover manual/chained, event-started, retry, structured loop, and
     date-wait execution.
   - Transpiler coverage verifies that a derived action and executable effect
     may share one stable semantic reference without the action disappearing
     during definition → canvas → definition validation.
   - Draft actions are persistent, activation validates first, dirty/operation
     state is visible, and both side rails are independently collapsible with
     narrow-layout overlays.
